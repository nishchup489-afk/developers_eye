## Session and transaction boundaries

Reviewed 2026-11-08 across backend, crawler and indexer. No transaction is held across a network request.

| Where | Boundary |
| --- | --- |
| Search API | One read-only session per request with a local `statement_timeout`. The connection stays checked out during ranking. |
| Frontier claim | One short transaction, committed before any fetch. |
| `process_job` | Attempt row committed before HTTP. Robots reads and writes commit one statement at a time. `_finalize` is one transaction for target, documents, links and attempt. |
| Politeness | Own short transactions, never inside a job transaction. |
| Indexer | Read session closed before analysis. The writer is one transaction holding the document row lock. |
| Vocabulary drain | One transaction per batch, with its queue deletes. |
| Event purge, reindex | Short batches. |
| Seeding | One transaction at startup, no network inside. |

Two things to watch. The deploy config allows 16 concurrent searches against 13 pooled connections (`DB_POOL_SIZE` 8 plus overflow 5), so the last few wait on the pool for up to `db_pool_timeout_seconds`. `sync_sources_once` keeps one connection idle in a transaction while seeding, so seeding longer than the 5 minute `idle_in_transaction_session_timeout` would abort startup.

## Rules for future changes

- Import every new model in `backend/src/backend/models/__init__.py` before running `alembic revision --autogenerate` (INC-0001).
- Read every autogenerated revision before committing; an `upgrade()` that is only `pass` is a bug (INC-0001).
- Never edit a revision that may already be applied; add a new forward revision (INC-0001). The only exception is ADR-0047.
- A new NOT NULL column on a table that can have rows needs a default or backfill in the same revision (INC-0034).
- Review generated migrations before applying them.
- Do not drop/truncate live derived data as an undocumented migration workaround.
