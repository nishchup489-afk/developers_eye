# INC-0034: code_vector migration failed on a populated search_index

## Signature

```
sqlalchemy.exc.IntegrityError: (NotNullViolationError) column "code_vector" of relation "search_index" contains null values
[SQL: ALTER TABLE search_index ADD COLUMN code_vector TSVECTOR NOT NULL]
```

## Summary

Revision 28efc23fadfc added `code_vector` as NOT NULL with no default, so `alembic upgrade` stopped on any database that already had rows in `search_index`. No data was lost and the running database was not affected, because it already had the column. The risk was to anyone upgrading an older populated database, such as a restored backup.

## Expected vs actual

- Expected: an upgrade from e94b530df145 keeps existing index rows and reaches head.
- Actual: the upgrade failed at 28efc23fadfc and the only workaround was to truncate `search_index`.

## Timeline

The risk was noted in `technical_handoff.md` and the database-schema overview. The audit checklist then ticked "tested against a populated pre-migration database" from a full chain run on a copy of the real database. That run could not have exercised this step with rows present, because the failure is unconditional when rows exist. A targeted test on 2026-11-08 reproduced it.

## Root cause

Alembic autogenerated the column as NOT NULL with no default, and PostgreSQL has to give existing rows a value when the column is added.

## Fixes that did not work

| Attempt | Why it failed |
| --- | --- |
| Truncate `search_index` before upgrading (documented workaround) | Search is empty until the indexer rebuilds everything, and it is a manual step that ADR-0022 rules out |
| A later forward revision | Alembic has to pass 28efc23fadfc first, so a later revision never runs on the affected databases |

## Resolution

The revision now adds the column with a temporary `''::tsvector` default, removes the default, and sets `indexed_hash` to `v0:` plus zeros. Only the indexer can build a real code vector, because it needs the Python analyzer. The `v0:` prefix makes every existing row look outdated to `_outdated_index_condition`, so the indexer rebuilds them while the text index keeps serving. The resulting schema is identical, so databases already past this revision need nothing.

## Prevention

- Regression test: `backend/tests/integration/test_migrations.py` upgrades a populated database through this revision and on to head.
- Monitoring / alert: none needed.
- Design change (ADR): ADR-0047 records when an applied revision may be edited.
- Remaining risk: another NOT NULL column added without a backfill would fail the same way. The test only covers this revision.

## Rules for future changes

- A new NOT NULL column on a table that can have rows needs a default or backfill in the same revision.
- A checklist tick for a populated upgrade needs a test that has rows at the revision under test.
